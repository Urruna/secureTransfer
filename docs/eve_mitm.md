# 链路中间人（MITM）攻击证据

> 对应 `project_q1.md` 的攻击测试要求：**窃听 / 篡改 / 伪造 均不可行**。
> 本文记录的是"**真实第三方进程**"级别的证据：攻击者不是通信端点自己，
> 而是一个独立进程，坐在 Alice 与 Bob 的 TCP 链路中间。
>
> 与本文配套：
> * 窃听（Eve 只能看到密文）→ [`eavesdrop.md`](eavesdrop.md)（Wireshark 抓包）；
> * 端点视角的篡改 / 重放 / 伪造 → `tests/integration/test_{tamper,replay,forge}.cpp`。

---

## 1. 结论摘要

```text
Alice ──connect──▶ [ eve 中继 :9400 ] ──connect──▶ Bob :9000
                     （独立进程，没有任何密钥）
```

| 中间人尝试 | 结果 | 被拦在哪里 |
| --- | --- | --- |
| 纯转发（当 TCP 代理） | **会话正常建立**，数据完整传输 | 拦不住 —— **这正是要展示的结论**：协议不依赖链路可信，"站在链路上"≠"能攻破会话" |
| 读取流量 | 只能看到密文 / Nonce / Sequence / SessionId / CMAC | — |
| 篡改（改密文 + 改序号） | 被拒绝，会话终止 | **⑦ CMAC 完整性校验失败** |
| 重放（截下来再发一遍） | 被拒绝，会话终止 | **⑥ 序号重放（防重放拦截）** |
| 丢弃（不转发） | **防不住**：对端只能等到超时 | 密码学防不了可用性攻击（见 §5） |
| 延迟（扣住再转发） | **防不住**：表现为业务变慢 | 同上 |
| 冒充 Bob（假服务端） | 握手失败 | HELLO_ACK 需要 K_master 签名，签不出来 |
| 修改 HELLO 里的身份字段 | 当时看不出来，AUTH 时暴露 | ③ 认证关 |

**一句话**：中间人能让会话建立、能让会话**断掉**，但拿不到明文、改不了内容、
冒充不了任何一端。

### 1.1 攻击者自己能看到什么（回答"Eve 窗口里为什么只有一句 ok"）

跑三窗口演示时，Bob 窗口会打印得很详细（`CMAC verification failed`、
`Replay Attack Detected`、回执内容），而 Eve 窗口只显示"已注入"。**这不是 bug，
是设计要的性质**：

| 信息 | Eve 能否得到 | 为什么 |
| --- | --- | --- |
| 包被转发/被改过 | ✅ 她自己干的 | — |
| 对端是否接受该包 | ❌ | 判定发生在**受害端进程内部**；中继只看到后续字节 |
| 对端拒绝的原因（哪一关） | ❌ | 受害端的处置/回执是**发给合法对端**的，走加密通道，Eve 只看到密文 |
| 连接随后被关闭 | ✅（旁证） | 但这只能说明"出事了"，说明不了"为什么" |

如果攻击者能拿到"接受/拒绝"的反馈，就相当于得到一个 oracle，可以据此二分猜测
内容或密钥位 —— 所以"攻击者拿不到判定"本身就是安全属性的一部分。
中继现在把这件事写清楚：措辞从 `result=ok` 改成 **`result=injected`**，
并在连接结束时打一行 `OBSERVE attacker_view=injected_only …`。

## 2. 为什么必须做成独立进程

项目里原本的"攻击演示"（`alice --attack`、界面上的篡改/重放按钮）本质是
**通信端点自己构造攻击包、用自己的连接发出去**（`SecureSession::sendRawWireForTesting`）。
安全结论没错——对端确实拒了——但它证明的是"收包方会校验"，而不是
"链路上的第三方攻不进来"。答辩时很容易被问："这是你自己改自己的发送路径吧？"

`eve` 中继补上了这一环：它是一个**独立进程**，两端都只是把它当成普通对端：

* Alice 主动连到 Eve 的端口（在 Alice 眼里，这就是"服务端地址"）；
* Eve 再连 Bob（在 Bob 眼里，这就是"客户端"）；
* 协议本身不绑定 IP/端口，也不依赖链路可信，所以 Alice/Bob 都不会察觉中间有人。

它**没有 K_master、没有 K_session，也不实现任何密码学逻辑**——只做
"收帧 → （可选）破坏 → 转发"，解析用的是项目自己的 `Frame` / `Packet`。

## 3. 两种用法

### 3.1 命令行（适合脚本与复现）

```bash
# 终端 1：真正的服务端
./bob.exe 9000 --out-dir experiment_data/received

# 终端 2：中间人（监听 9400，转发到 9000）
./eve.exe --listen 9400 --target 127.0.0.1:9000
#   运行中可以随时输入命令（<目标> 见下）：
#     tamper <目标>           篡改后转发
#     replay <目标>           原样重发
#     drop   <目标>           丢弃，不转发
#     delay  <ms> <目标>      延迟转发
#     status / quit
#
#   <目标> 有四种写法（可组合）：
#     （省略）                  下一个包
#     --type DATA             下一个 DATA 包（也可 FILE_CHUNK / IMAGE）
#     --last --type DATA      最近一条 DATA —— 捕获-篡改/重发，立即下手
#     --index 7               第 7 个「匹配类型」的包：
#                              没写 --type 时 = 该方向第 7 个包（**含 4 个握手包**）
#                              写了 --type DATA 时 = 第 7 条 DATA（不受握手干扰）
#     --dir c2s|s2c|both      方向（默认 c2s）
#   旧写法 [n] [dir] 仍然可用，例如 `tamper 5 c2s`
#
#   ⚠ 序号必须指向"将来"的包。填了已经过去的序号会立即回一行 ERR 并说明该填什么，
#     不会像早期版本那样静静挂在队列里（那会让人以为"点了没反应"）。

# 例：把"下一条短消息"改掉（不用再数第几个包）
#     tamper --type DATA
# 例：把刚才那条短消息抓回来改一个字节再发（上课演示最直观的一种）
#     tamper --last --type DATA

# 终端 3：客户端——注意端口写的是**中继的端口**
./alice.exe 127.0.0.1 9400 --file experiment_data/test_file_64KB.bin
```

### 3.2 图形界面（适合演示）

界面里的 **Eve 攻击演示 → 「中间人链路」页签**：

1. 填"监听 9400 / 转发到 9000"，点 **[启动中继]**（界面会用 QProcess 拉起 `eve.exe`）；
2. 本端"对端地址/端口"指向中继（127.0.0.1:9400），点 **[连接]**；
3. 回到 **「攻击演示」页签**，来源选"中间人"，方式选篡改/重放/丢弃/延迟，
   **目标**选"下一条短消息 / 最近一条短消息 / 下一个文件块 / 指定第 N 个包"，
   点 **[发起攻击]** —— 攻击指令通过 stdin 下发给中继；
4. 对端的判定回执会回到界面，**8 关流水线**里命中的那一关会高亮，
   「攻击历史」页签会记下"时间 / 来源 / 方式 / 拦截关卡 / 结果"并可导出 CSV。

想一键跑完整套，用 **[一键攻击剧本]**（或命令行 `--scenario`）：
自动按"篡改 → 重放 → 丢弃"跑三轮，每轮自动重启中继、重连、发探针消息、归档结果。

## 4. 实测记录（2026-10-10，Windows / MSYS2 MinGW-w64）

配置：Bob 常驻 `9930`，中继监听 `9400` → 转发到 `9930`，界面作客户端。

| 轮次 | 中继动作 | 受害端（Bob）的实际反应 | 统计 |
| --- | --- | --- | --- |
| 1 | `tamper`（篡改第 5 个 C2S 包 = 第一条业务数据） | `CMAC verification failed - Message rejected` | `rejectedMac=1` |
| 2 | `replay`（把刚转发的数据包再发一遍） | `Replay Attack Detected: 序号 1 不大于已接收的最大序号 1` | `rejectedReplay=1` |
| 3 | `drop`（丢掉第一条业务数据） | `recv() 超时，已接收 0/4 字节` → 会话终止 | 无拒绝计数（**防不住**） |

累计统计：`reject(format/replay/mac/state)=0/1/1/0`，`handshake(ok/fail)=3/0`。

中继自己那侧的日志（`experiment_data/relay_log.txt`）长这样 —— 注意措辞是
**"已注入"**而不是"成功"，而且它会如实记录"能观察到什么"：

```text
QUEUED kind=tamper dir=C2S target=next
ATTACK kind=tamper dir=C2S n=5 result=injected（已注入到链路；对端是否接受由受害端掌握）
OBSERVE attacker_view=injected_only injected=1 closed_after_last_inject_ms=1 \
        note=连接在注入之后被关闭（是否因为被拦下，Eve 无从得知；判定只发生在受害端）
```

三轮回执/观察的时间差很说明问题：篡改那轮连接在注入后 **1 ms** 就被关闭；
丢弃那轮则是 **9611 ms**（正好是对端的 IO 超时）。攻击者能看出"出事了"，
但**看不出为什么**。

另外，受害端在终止前会回一条攻击回执（见 `docs/protocol.md` §6.3）：

```text
ATTACK-REPORT: ⑦ CMAC 完整性校验失败 | seq=0 | CMAC verification failed: 数据包完整性校验未通过，已拒绝该消息
ATTACK-REPORT: ⑥ 序号重放（防重放拦截） | seq=1 | Replay Attack Detected: 序号 1 不大于已接收的最大序号 1
```

这条回执走的是**正常加密通道**，因此它会穿过中继回到攻击端——攻击端的界面
才能显示"我倒在哪一关"。

### 4.1 自动化测试

同一个中继核心（`src/attack/mitm_relay.cpp`）也被集成测试以线程方式复用：

```bash
ctest --test-dir build-win -R test_mitm --output-on-failure
```

四条用例分别断言：纯中继下会话/双向消息正常；篡改 → `rejectedMac==1`；
丢弃 → 只有超时、没有拒绝计数；重放 → `rejectedReplay==1`。

两个平台都跑过：Windows（MSYS2 MinGW-w64 / Qt 5.15.19）与
Ubuntu 20.04（g++ 9.4 / Qt 5.12.8）均为 **18/18 通过、0 编译告警**。
Linux 侧第一次构建时暴露了两个只有该平台才会出现的问题（缺少 `<fcntl.h>`、
`send()` 触发 `SIGPIPE` 直接杀进程、`pthread` 未链接），已修：
`send()` 统一带 `MSG_NOSIGNAL`，`eve` 目标显式链接 `Threads::Threads`。

## 5. 必须如实写进报告的 limitation：可用性攻击防不住

`drop`（丢弃）与 `delay`（延迟）这两种攻击，**密码学层面没有任何办法防御**：

| 攻击 | 密码学能做什么 | 实际表现 |
| --- | --- | --- |
| 丢弃一个包 | 不能阻止丢弃 | 接收方等到超时，会话终止（DoS 的一种） |
| 延迟转发 | 不能阻止延迟 | 业务变慢；CTR 模式不会因此泄漏密钥流 |
| 断链 | 不能阻止断链 | 会话失败，需要重连 |

能做的只有"检测与恢复"：超时判失败、重新建链、审计留痕。把"防不住可用性攻击"
写清楚，比假装防住了更有价值——这也是本项目在报告里刻意保留的一节。

## 6. 实现要点（踩过的坑）

1. **裸 socket 而不是复用 `Network`**：中继需要"两个连接、两个方向"同时收发，
   而 `Network` 是为"一条加密会话"设计的（内部有会被两个线程同时写的
   `lastError_` 等状态）。攻击者侧工具也不该复用受害端的会话语义。
   帧的解析仍然复用 `Frame` / `Packet`，保证"中继看到的字段"与协议定义永不脱节。
2. **Windows 的端口占用陷阱**：Windows 允许 `0.0.0.0:P` 与别人的
   `127.0.0.1:P` **同时绑定**，而发往 127.0.0.1 的连接会被更具体的绑定抢走。
   实测本机 `9430` 被另一个服务占着，中继"显示 LISTEN 成功、却一个连接都收不到"，
   客户端连上后收到的竟是那个服务的 HTTP 响应。现在中继在绑定**之前**会先探测
   `127.0.0.1:P` 上是否已有活监听，冲突就直接报错，不再出现"看起来成功"的失败。
3. **中继进程必须随连接结束而退出**：图形界面是用管道喂命令的，如果主线程阻塞在
   读 stdin 上，就永远发现不了"连接已断"，进程会赖着不走、端口不释放，
   下一次演示就撞上"端口被占用"。现在 stdin 由独立线程读取，主线程只盯连接状态。
4. **重放要"复制刚转发的包"**：早期实现是"重放上一个已转发的包"，若在握手刚结束
   时触发，被重放的会是最后一个握手包（KEY_CONFIRM）；收包方在数据阶段遇到握手包，
   会先在"消息类型不允许"那一关拒掉，看不到 ⑥ 防重放。改成复制当前包之后，
   重放的是同一条业务数据，稳定命中 ⑥ 关。

## 7. 这个程序为什么可以随发布包一起分发

`eve.exe` 是**课程攻防演示用的调试工具**，不是后门：

* 不含任何密钥，不能解密任何数据；
* 不能冒充任何一端（HELLO_ACK / AUTH 都需要 K_master 签名）；
* 不改协议、不伪造协议消息，只做"转发 + 破坏"，破坏必然被协议检测到；
* 它的存在反而**加强**了安全性结论：第三方进程亲自试过，仍然攻不进去。
