# 密码算法性能对比报告（自实现 vs 库实现）

> 对应课程要求 5 / `project_q1.md` §10：
> “将自己的密码算法实现与库文件或别人的代码实现进行全面的性能对比”，
> 并“结合算法实现方式、代码优化、底层硬件加速等因素进行解释”。

**结论先说**：默认情况下 OpenSSL 比我们的实现快 **4.7 ~ 82 倍**，
但把 OpenSSL 的硬件指令关掉、做“纯软件对纯软件”对比后，
差距缩小到 **2.7 ~ 3.6 倍**。也就是说，**数量级的差距主要来自 AES-NI 硬件加速，
而不是算法实现本身“算错了”或“算法不同”**；
剩下的 2~3 倍差距来自工程优化（汇编、多分组并行、缓存复用）。

## 1. 测试环境与方法

| 项目 | 说明 |
| --- | --- |
| 机器 | VMware Workstation 17 虚拟机 Ubuntu6.21（2 vCPU / 4 GB） |
| 系统 | Ubuntu 20.04.6 LTS，内核 5.15.0-140 |
| 编译器 | g++ 9.4.0，`-O3`（CMake `Release`） |
| 对比库 | OpenSSL 1.1.1f（`libssl-dev`，EVP 接口） |
| CPU 能力 | 支持 AES-NI（`/proc/cpuinfo` 的 `aes` 标志） |
| 测试程序 | `tools/crypto_benchmark.cpp`（本工程，独立可执行文件） |

**公平性措施**

1. 两侧处理**同一份数据**、同一把密钥、同一个 nonce/IV；
2. 都按“**一次性调用**”计时——我们的 `AES::ctrXor` 每次含密钥扩展，
   OpenSSL 每次含 `EVP_EncryptInit`，这正是两者在真实系统里的调用方式；
3. 每档先**预热 1 次**，再重复多次取平均（重复次数按数据规模自适应，最少 3 次）；
4. 单线程、无并行、无多缓冲优化；
5. **先做正确性交叉验证**再比性能，避免“快的实现算错了”（见 §4）。

**两组对比**

* 第 1 组：默认运行（OpenSSL 自动使用 AES-NI 硬件指令）；
* 第 2 组：`OPENSSL_ia32cap=~0x200000200000000` 运行（禁用 AES-NI 等硬件指令，
  得到 OpenSSL 的**纯软件实现**）。

复现命令：

```bash
cd /home/securityTransfer/build
./crypto_benchmark                        # 默认，跑到 100 MB
OPENSSL_ia32cap=~0x200000200000000 ./crypto_benchmark --max-mb 10   # 纯软件对比
```

## 4. 正确性交叉验证（比性能之前先做）

用 RFC 4493 的测试密钥与消息，分别用自实现与 OpenSSL 计算：

```text
AES-128-CTR 密文
  自实现  : a38b4e543d03c2cb78bffe0be84a2521
  OpenSSL : a38b4e543d03c2cb78bffe0be84a2521     → 一致 ✅

CMAC（RFC 4493 的 16 字节向量）
  自实现  : 070a16b46b4d4144f79bdd9dd04a287c
  OpenSSL : 070a16b46b4d4144f79bdd9dd04a287c     → 一致 ✅
```

结论：两侧算的是**同一个结果**，因此后面的性能数字是可比的；
我们的实现不仅在 RFC 4493 标准向量上正确，也与 OpenSSL 逐字节一致。

## 5. 结果分析（结合实现方式、代码优化与硬件加速）

### 5.1 数量级差距来自硬件加速

同一台机器、同一份数据，只把 OpenSSL 的 `OPENSSL_ia32cap` 改成禁用 AES-NI：

| 指标 | 默认（有 AES-NI） | 禁用 AES-NI |
| --- | --- | --- |
| AES-CTR 库实现吞吐率 | 8222 ~ 9408 MB/s（64 KB ~ 1 MB） | 329 ~ 331 MB/s |
| AES-CTR 的库/自实现倍率 | 70 ~ 82 倍 | 2.8 ~ 2.9 倍 |
| CMAC 库实现吞吐率 | 1600 ~ 1773 MB/s | 372 ~ 383 MB/s |
| CMAC 的库/自实现倍率 | 14 ~ 17 倍 | 3.3 ~ 3.5 倍 |

**解释**：AES-NI 是一条 CPU 指令完成一轮（SubBytes + ShiftRows + MixColumns + AddRoundKey），
OpenSSL 在 x86-64 上默认走汇编 + AES-NI 路径，一次处理多个分组；
我们的实现是 C++ 逐字节查表（S 盒 256 字节表 + `xtime` 移位）逐分组串行处理，
因此单分组指令数相差一到两个数量级。

### 5.2 纯软件对比时的 2~3 倍差距来自工程优化

禁用硬件指令后，OpenSSL 仍然快 2.7 ~ 3.6 倍，原因在实现层面而非算法层面：

| 差异点 | OpenSSL 软件实现 | 我们的实现 |
| --- | --- | --- |
| 语言与指令 | x86-64 / ARM 手写汇编，寄存器分配精细 | C++，编译器自动优化 |
| 并行度 | 向量化（VPAES/位切片），多分组并行 | 逐分组串行，16 字节一轮 |
| 查表方式 | T 表 / 位切片，减少访存次数 | 每字节查 S 盒 + `xtime` 移位 |
| 循环结构 | 展开、减少分支 | 普通 for 循环 |

结论：我们的实现**算法正确、结构清晰**，差距属于“没有做底层优化”，
在课程语境下是合理取舍（可读性优先，且要求是“自己实现”）。

### 5.3 CMAC 的差距为什么比 AES-CTR 小

CMAC 本质是 CBC-MAC（串行依赖），**天然无法并行**，所以：

* 硬件加速只能加速“每个分组的那一次 AES”，不能加速整体串行结构
  → 默认情况下库/自实现是 15 倍，低于 AES-CTR 的 70~82 倍；
* 纯软件下是 3.3~3.5 倍，与 AES-CTR 的 2.7~2.9 倍接近，
  额外差距来自我们每次调用会重复做密钥扩展与 K1/K2 子密钥推导，
  而 OpenSSL 复用 `CMAC_CTX` 上下文。

### 5.4 数据规模会改变“倍率”：100 MB 时差距缩小到 4.7 倍

| 数据大小 | 库实现吞吐率（有 AES-NI） | 倍率 |
| --- | --- | --- |
| 1 MB（在 CPU 缓存里） | 8222 MB/s | 70.33x |
| 10 MB | 4311 MB/s | 37.62x |
| 100 MB（远超缓存） | 526 MB/s | 4.72x |

**解释**：AES-NI 的计算速度已经超过内存读写速度，数据量大到装不进 CPU 缓存时，
库实现变成**内存带宽受限**；我们的实现始终是**计算受限**（≈111 MB/s 不随规模变化）。
因此“快多少倍”必须连同数据规模一起报告——这也是课程要求列出 1 KB~100 MB 多档的原因。

### 5.5 加解密耗时基本对称

CTR 模式下加密与解密是同一个运算，实测两侧的加密/解密时间都只差几个百分点
（例如自实现 1 MB：8.553 ms / 8.697 ms），与理论一致，说明实现没有引入额外分支。

### 5.6 固定开销（密钥扩展）可以忽略

| 项目 | 实测值 |
| --- | --- |
| 单次密钥扩展 `aes128_key_expand` | 0.036 µs |
| 占 1 KB 加密耗时比例 | 0.4% |
| 占 64 KB 及以上 | 0.0%（可忽略） |

也就是说，即使把密钥预扩展缓存起来，对本实验的数据规模几乎没有收益；
真实系统里值得做的是**多分组并行 + 硬件指令**（见 §6）。

## 6. 可以进一步优化的方向（写报告讨论用）

1. **使用 AES-NI**：用 `_mm_aesenc_si128` 等内建函数替换查表实现，
   预计可把吞吐率提高一个数量级（但这偏离“纯软件自实现”的教学目标，
   可作为“扩展实验”单独展示）；
2. **CTR 模式多分组并行**：CTR 的每个分组互不依赖，可一次生成 4~8 个分组密钥流，
   配合循环展开与 T 表，预期提升 2~4 倍；
3. **减少每块访存**：用 T 表（4×1 KB）把 SubBytes+ShiftRows+MixColumns 合并成 4 次查表；
4. **CMAC 复用密钥与子密钥**：把 `CMAC::generate` 的密钥扩展与 K1/K2 推导移到上下文初始化，
   避免每条消息重复计算；
5. **编译层面**：`-O3 -march=native -funroll-loops`（需注意与“可移植性”的取舍）。

## 7. 结论

1. **正确性**：自实现的 AES-CTR 与 CMAC 输出与 OpenSSL **逐字节一致**，
   且通过 FIPS-197 / NIST SP 800-38A / RFC 4493 标准向量；
2. **性能**：默认（库使用 AES-NI）时库快 4.7~82 倍，
   纯软件对比时只快 2.7~3.6 倍——**差距的主因是硬件加速，其次是工程优化**；
3. **规模效应**：倍率随数据规模变化（1 MB 时 70 倍，100 MB 时 4.7 倍），
   报告性能必须写明数据规模；
4. **对系统的影响**：本工程单条消息上限 1 MB，实测加密+CMAC 合计约 9~10 ms/MB，
   在教学演示场景下完全够用；瓶颈在于纯软件实现，而非协议设计。

### 8.4 迁移中发现并修复的一个真实缺陷

原先的 `cpuAesCapability()` 只读 `/proc/cpuinfo`；Windows 上该文件不存在，
于是程序**永远**打印"不支持 AES-NI（OpenSSL 也只能用软件实现）"，
而实际上这台 i5-1340P 是支持 AES-NI 的。这会让"倍率"的解释彻底说反：
把"库用了硬件加速"误说成"实现水平差距"。

修复方式：Windows 分支改用编译器内建检测（`__builtin_cpu_init()` +
`__builtin_cpu_supports("aes")`），检测结果已与 `OPENSSL_ia32cap` 开关的行为互相印证
（禁用硬件加速后库的吞吐率确实按预期下降到 500~570 MB/s 一档）。

### 8.5 结论

Windows 侧与 Linux 侧在**机制层面完全一致**：

1. 默认情况下库快一个数量级（AES-CTR 12~23 倍），主因是 AES-NI；
2. 禁用硬件加速后差距收缩到 **2.5~4.4 倍**，属于工程实现水平（汇编、多分组并行、查表）的差距；
3. 编译环境从 g++ 9.4 换成 g++ 16.2、OpenSSL 从 1.1.1 换成 3.6.5，
   自实现的吞吐率仍稳定在 **120~140 MB/s**，说明性能结论对编译器/库版本不敏感。

5. **两组数据**：
   * 默认组：各库按发行包默认配置（大概率启用 AES-NI）；

| 10 MB | 140.9 | 1956.9（13.89x） | 1170.7（8.31x） | 945.7（6.71x） | 333.9（2.36x） | 315.2（2.23x） | 69.7（0.49x） |
| 100 MB | 138.1 | 1981.6（14.35x） | 1150.5（8.33x） | 935.3（6.77x） | 410.2（3.00x） | 324.5（2.37x） | 68.7（0.50x） |

## 9.4 结论：差距来自"硬件加速"与"工程优化"两层，而不是"算法不同"

1. **硬件加速是数量级差距的主因**：同一个库（OpenSSL）关掉 AES-NI 后从 4272~5926 MB/s
   掉到 648~651 MB/s，差距 ~7~9 倍；Mbed TLS 从 ~1170 掉到 ~390（~3 倍）。
2. **同一个硬件加速，不同库的用法也不同**：都用 AES-NI 时，
   OpenSSL/Botan 能到 3900~5900 MB/s，而 Mbed TLS 只有 ~1170 MB/s。
   原因是 Mbed TLS 的 AES-NI 路径按"一次一块（16 字节）"调用硬件指令，
   没有做多块并行/流水线，而 OpenSSL/Botan 会一次处理多个分组。
   —— 这说明**"是不是库"并不决定性能，"有没有把硬件/流水线用好"才决定**。
3. **纯软件对纯软件时我们处在什么水平**：
   * 比 Mbed TLS 慢 **2.9~3.0 倍**（它用 T 表 + 优化的循环，我们是最朴素的实现）；
   * 比 OpenSSL 软件路径慢 **4.8~5.0 倍**（它还做了多块并行与汇编级优化）；
   * **与 Botan 的通用软件路径基本持平（1.11~1.14 倍，1 KB 时我们还更快）**，
     CMAC 上我们反而比它快约 2 倍。
   也就是说，我们的实现属于"合格的通用软件实现"，差距是工程优化（查表、并行、汇编），
   不是算法错误——这一点有 §9.2 的逐字节交叉验证兜底。
4. **CMAC 的倍率普遍比 AES-CTR 小**：CMAC 是串行的 CBC-MAC 链（后一块依赖前一块），
   硬件加速的收益不如 CTR 这种可并行的模式；所以纯软件下库对我们的优势也小得多。

## 9.5 "纯软件对照"是怎么来的（可复现）

| 库 | 关闭硬件加速的方式 |
| --- | --- |
| OpenSSL | 运行时环境变量：`OPENSSL_ia32cap=~0x200000200000000`（无需重新构建） |
| Mbed TLS | 硬件支持是编译期宏 `MBEDTLS_AESNI_C`：用自定义配置头（把它注释掉）重新编译 `library/*.c`，得到 `libmbedcrypto_noaesni.a` |
| Botan | 硬件支持由构建时的模块决定：源码构建 `--minimized-build --enable-modules=aes,cmac,ctr,modes --disable-modules=aes_ni,aes_vaes --cc=gcc --build-targets=static` |

两个自建库都放在 `D:\AppGallery\dev-tools\libs\`（`mbedtls-noaesni/`、`botan-noaesni/`），
CMake 用 `-DST_BENCH_SOFT_ROOT=D:/AppGallery/dev-tools/libs` 指向它们，生成第二个可执行文件
`crypto_benchmark_soft.exe`；它与默认的 `crypto_benchmark.exe` 用同一份源码，
只是链接的库不同，因此**口径完全一致**。

> 关于 Botan：3.13 里 AES 只有"通用软件实现"与各硬件模块（`aes_ni` / `aes_vaes` / …），
> 并没有额外的 SIMD 软件实现，所以上述最小构建得到的正是它的纯软件路径，
> 对比是公平的（这一点在构建时核对过模块清单）。

## 9.6 怎么复现（一条命令）

```bash
# 在 MSYS2 的 MinGW64 shell 里（项目根目录）
bash scripts/run_benchmarks.sh              # 跑 100 MB 版本
bash scripts/run_benchmarks.sh --max-mb 10  # 快速版
```

脚本会依次跑"默认"与"纯软件"两组、导出 CSV、并用 `tools/bench_merge.py`
生成汇总表 `experiment_data/benchmarks/summary.md`。
单独跑也可以：

```bash
./build-win/crypto_benchmark.exe --csv hw.csv --label hw
OPENSSL_ia32cap=~0x200000200000000 ./build-win/crypto_benchmark_soft.exe --csv sw.csv --label sw
python3 tools/bench_merge.py hw.csv sw.csv -o summary.md
```
